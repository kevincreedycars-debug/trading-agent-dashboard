# Live Trading feed cadence (live-trading lane)

One read-only producer run per M5 bar, validated, logged, and scheduled - so the 5m chart is a feed rather than a
file somebody remembered to regenerate.

The dashboard reads `data/live-trading.json` and badges it `FRESH` or `STALE` against a 900-second window. Nothing
in the repository wrote that file on a clock, which is why the section read `STALE` at any hour the producer had
not been run by hand. This is that clock, and nothing else: the runner spawns the existing read-only producer,
checks the artifact with the page's own validator, writes one line of evidence per run, and a single Windows task
calls it every five minutes.

| File | Role |
| --- | --- |
| `run-live-trading-feed.js` | The runner. `--once` is one producer run, one validation, one log line, exit 0/1. `--loop` repeats at each 5m bar close. `--align` waits for the next close plus the settle window before running. |
| `publish-live-trading-feed.js` | The only step in this lane that writes to the branch GitHub Pages serves. Reached only when a run is given `--publish`, and only if its own gates pass. |
| `register-live-trading-feed-task.ps1` | Registers, prints or removes the one scheduled task (`LiveTradingFeedTick019`): a five-minute repetition, hidden window, no overlap, started when available. |
| `../tools/mt5-bridge/live-trading-snapshot.py` | The producer. The only process here that attaches to the terminal, and read-only by construction. |
| `../tools/mt5-bridge/live-trading-order.py` | The order tool: the only file in this lane that can place a trade, run by hand and never called by this cadence. It shares nothing with the runner, so nothing on this clock can send. |
| `validate_live_trading_feed.js` | The same validator the dashboard's guard uses; the runner refuses to call a run `ok` if it fails. |
| `../data/live-trading.json` | The artifact the page fetches. Rewritten by every run. |
| `../tmp/live-trading-feed.log` | One JSON line per run. Ignored by git, like everything else under `tmp/`. |
| `../tmp/live-trading-feed-run.cmd` | Generated by the registration script: the machine-specific node and python paths, with all the quoting the task's own command line must not carry. |
| `../tests/live_trading_feed_cadence.test.js` | 25 tests over the boundary arithmetic, the flags, the summary, the lock, every failure status, the aligned wait, working-directory independence and the read-only boundary. |
| `../tests/live_trading_feed_publish.test.js` | 24 tests over the publisher and over the runner's publish step: each gate's refusal, the retry after a rejected push, and the two ways a run publishes nothing. |

## Run it

```powershell
node scripts/run-live-trading-feed.js --once                      # one run now, one line printed and logged
node scripts/run-live-trading-feed.js --loop                      # run now, then at every 5m bar close, until Ctrl-C
node scripts/run-live-trading-feed.js --once --out tmp/check.json # write somewhere else (leaves the artifact alone)
node scripts/run-live-trading-feed.js --once --terminal "C:\Program Files\FTMO Global Markets MT5 Terminal"
node scripts/validate_live_trading_feed.js                        # the artifact on its own
node --test tests/live_trading_feed_cadence.test.js               # this runner's contract
```

Every path is resolved against the repository root, not the working directory: a scheduled task starts in
`C:\Windows\System32`, and a relative lock path there makes the run try to create `C:\Windows\System32\tmp`,
throw, and exit without writing a line of evidence. That fault was found by running the task, not by reading it.

The producer's own flags are passed through where they matter: `--terminal` becomes its `--path`, `--candles`
becomes its M5 count. Omitting `--terminal` means the producer's own terminal discovery, which is what the FTMO
guide uses.

## Publish it (off unless asked for)

The cadence writes on this machine. Publishing the artifact is a separate, deliberate act, because it is the only
thing in this lane that writes to the branch GitHub Pages serves:

```powershell
node scripts/run-live-trading-feed.js --once --publish --publish-dry-run   # run the gates; write and push nothing
node scripts/run-live-trading-feed.js --once --publish                     # one run, then publish if the gates pass
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/publish-live-trading-feed.js --dry-run --json
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/register-live-trading-feed-task.ps1 -Publish -Show
```

`scripts/publish-live-trading-feed.js` carries the decision, as four gates that each refuse with a reason rather
than warn:

1. The artifact passes the same `validate_live_trading_feed.js` the page's guard uses.
2. The artifact is inside its own `stale_after_seconds` window.
3. Its `generated_at_utc` is strictly newer than the copy already on the branch - compared on the snapshots' own
   clock, not on bytes, because git normalises line endings and a byte compare would republish the same read as a
   change.
4. At least `--min-interval-seconds` (default 600) has passed since the last publish. GitHub's soft limit of ten
   Pages builds an hour is a 360-second floor; 600 is six builds an hour and leaves headroom, so the task's
   five-minute repetition publishes every other bar at most.

It publishes by resetting its own checkout at `<canonical root>/.local/live-trading-feed-publish` to the remote
branch, copying that one file, committing, and pushing. Nothing else is touched, and the lane's worktree is never
written to. A push rejected as non-fast-forward is retried once against the branch as it now stands, then refused.
The gate order matters: an interval hold is answered from the state file alone, so a run inside the cadence does no
git work at all. The last publish is recorded in `tmp/live-trading-publish-state.json` (ignored) with the
generated-at it carried, the commit, and the count.

A run asked to publish that could not is a failed run: the artifact is still written and validated, the log line
carries `publish.action` and its reason, and the exit status is non-zero - a scheduler surfaces only that. `--force`
overrides the interval gate alone, never a validation, freshness or "already newer on the branch" refusal.

Since `live-trading-feed-v3` the artifact this cadence writes also carries what was executed: `positions`,
`closed_trades` and the `history` window they were paired over. The cadence does nothing with them beyond validating
them and publishing them, but its log line reports them - `positions_open`, `closed_trades` and
`closed_trade_window_days` - so every run's own line of evidence says whether the account held anything and whether
anything closed inside the snapshot's window. A run that shows a trade appearing or closing is therefore visible in
`tmp/live-trading-feed.log` without opening the artifact, and `null` there means the snapshot predates the read-back.

On this machine the cadence is armed: the task was registered with `-Publish` at `14:22:40+01:00` on 2026-10-04, its
wrapper carries `--publish --publish-min-interval-seconds 600`, and its first unattended publish was the `13:30:20Z`
read (`commit 6de4571`, `tmp/live-trading-publish-state.json` at `publish_count: 1`). Disarming is the same command
without the switch, and note the registration script rewrites the wrapper before it honours `-Show`, so a `-Show`
run with a different publish setting changes what the task will execute next.

## The task

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/register-live-trading-feed-task.ps1 -Show     # plan only
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/register-live-trading-feed-task.ps1 -Test     # prove the launcher
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/register-live-trading-feed-task.ps1           # register and start
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/register-live-trading-feed-task.ps1 -Remove    # take it away
```

`-Test` registers a throwaway task with the same launcher and runtime but a wrapper without `--align`, starts it
through the scheduler, waits up to a minute for a new log line and reports the verdict, then removes the throwaway.
It exists because the two faults below are invisible in the source and only appear when the scheduler runs the
thing: a launcher chain can hang, or exit 1, while every file in the repository looks correct.

| Fault | What it did | Fix |
| --- | --- | --- |
| Task Scheduler doubles quotes inside an argument it stores | The command line carried quotes of its own, so the hidden launcher received a mangled command: the instance stayed alive for four minutes, attached to no terminal and wrote nothing. | The command the task passes is quote-free, `cmd.exe /c <wrapper>`, and every quote lives in `tmp/live-trading-feed-run.cmd`, where cmd.exe's own rules apply. The wrapper path may not contain a space, and the script says so rather than registering something that cannot work. |
| A scheduled task starts in `C:\Windows\System32` | The runner's relative default lock path made it try to create `C:\Windows\System32\tmp`, throw EPERM and exit 1 with no log line. | The runner resolves `--out`, `--log` and `--lock` against the repository root, and any unexpected error is logged with `status: "error"` instead of escaping the run. |
| `-Show` writes the wrapper before it prints the plan | Reading the plan is enough to change what the registered task runs next: the script generates `tmp/live-trading-feed-run.cmd` first, so a `-Show -Publish` from a checkout rewrites the command line of the live task, and a plain `-Show` rewrites it back. | Read the plan with the flag question in mind, and check the wrapper's last line before leaving a checkout. The task is bound to the wrapper of whichever checkout registered it - on this machine the lane worktree `.local/worktrees/live-trading`, not the canonical root. |

It registers `LiveTradingFeedTick019` as one five-minute repetition of
`node scripts/run-live-trading-feed.js --once --align --quiet`, launched through the same `run-hidden.vbs` the
Gold capture window uses so the window never flashes, with `MultipleInstances` at `IgnoreNew` and
`StartWhenAvailable` on. `--align` is the point of the task: each run sleeps to the next M5 close plus the
20-second settle window, so a repetition grid that has drifted still samples just after the bar it reads closed.
`-Publish` adds `--publish --publish-min-interval-seconds <n>` to that command, which is the only difference
between a cadence that writes the file and one that also keeps the published dashboard current; the plan `-Show`
prints says which one the wrapper would carry (`publishes_anything`).
The task result codes worth reading are `0` (finished), `267009` (running, still aligning) and `2147946720` /
`0x800710E0` (refused because the previous run is still aligning - expected, not a failure).

Re-running the script stops and removes any previous registration first. That is deliberate: registering over a
task whose run was still aligning (the `-Force` form) left the scheduler reporting the task as running and then
refusing every repetition, so the cadence stopped while every file looked correct. `Register-ScheduledTask` with an
interval and no duration is an indefinite repetition on this engine - checked with a one-minute probe task on
2026-10-04, which fired twice as registered, and it is the same shape the Gold capture window has been running for
weeks. A bounded `-RepetitionDuration` is not the fix and `[TimeSpan]::MaxValue` is refused by the task XML.

## The log line

One JSON object per run, appended:

```json
{"at_utc":"2026-10-04T11:36:05.148Z","status":"ok","out":"data/live-trading.json","producer_exit":0,
 "generated_at_utc":"2026-10-04T11:36:06.146721+00:00","feed_age_seconds":0,"stale_after_seconds":900,
 "snapshot_stale":false,"account":"***614 FTMO-Server","positions_open":0,"live_ticks":1,"quiet_ticks":3,
 "instruments":[{"symbol":"BTCUSD","bid":85253.36,"tick_age_seconds":4,"live_tick":true,
 "m5_bar_age_seconds":62,"m5_stale":false}, ...]}
```

`status` is `ok`, `invalid` (the artifact exists but the validator rejects it), `producer_failed` (no terminal, or
the interpreter did not start), `unreadable` (the run wrote nothing parseable), `skipped` (another run holds the
lock) or `error` (something unexpected, most often a path the run cannot create - reported rather than thrown so a
quiet failure still leaves evidence). A run given `--publish` carries one extra object, and only on a valid
artifact:

```json
"publish":{"action":"published","published":true,"decision":"publish","reason":null,
 "commit":"0a64ec5","attempts":1,"min_interval_seconds":600}
```

`action` is `published`, `would_publish` (dry run), `unchanged` (the branch already carries this read or a newer
one), `too_soon` (inside the interval, decided from the state file before any git work), or `refuse` (the artifact
failed validation, or is outside its freshness window, or the push did not land). Only `refuse` makes an otherwise
successful run exit non-zero.
`live_ticks` / `quiet_ticks` are the one fact the artifact cannot give: an
instrument is counted live only
if it ticked within one M5 bar of the snapshot's own clock. The producer's `m5_stale: false` for a market shut
since Friday is not a live read - that flag compares the newest bar with the instrument's own last tick, and a
shut market's closing bar is still the newest bar it has. Both numbers sit in the same line so nobody has to
re-derive which one is liveness.

## What it will not do

There is no order path: no send, modify, close or cancel call, no order function anywhere in the runner or the
task script, and the producer it calls is allowlisted to reads. It carries no credential, reads no account data
beyond the masked line the producer already publishes, and touches no warehouse, workflow or Layer 1 artifact. The
runner commits and pushes nothing itself: unless a run is given `--publish`, the artifact is rewritten on this
machine only, and the GitHub Pages copy of the dashboard changes only when somebody commits it. With `--publish`
the run hands the artifact to the publisher above, which does the git work in its own checkout after its four
gates pass; the cadence is scheduled to publish only when the registration asked for it. A run is not a signal, an
entry or an edge.

## Tests

```powershell
node --test tests/live_trading_feed_cadence.test.js tests/live_trading_feed_publish.test.js tests/live_trading_feed.test.js tests/l2l_levels.test.js
```

25 cadence tests, 24 publish tests, 34 feed tests and 48 levels tests, all local. The runner is exercised against
the committed artifact and a stand-in producer process, so the validation, the lock, the log and every failure
status are real. The publish tests go one step further and replace git itself with a recorded stand-in - including
a queue of push results, so a rejected push and its single retry are asserted without a remote - so nothing in
either suite attaches to a terminal, touches a remote or writes outside the system temp folder. Running the
publisher by hand is the one command here that reaches the remote, and `--dry-run` is what stops it before it does.

## The honest limits

1. The published page still only changes when the cadence publishes, and publishing is off unless asked for. Even
   with `-Publish`, the interval gate holds it to at most six Page builds an hour rather than one per bar, which
   would be roughly 288 commits a day into production `main`.
2. The artifact is tracked, so the worktree is dirty from the first run until the task is removed (`-Remove`).
3. Three of the four instruments cannot show a live 5m candle outside the trading session, and the log says so
   rather than dressing their Friday closing bar as a live read.
4. A cadence is not a model. Running the producer every five minutes says the 5m read is current; it says nothing
   about the entry rule, the exit rule or an edge, which are the next two builds.
