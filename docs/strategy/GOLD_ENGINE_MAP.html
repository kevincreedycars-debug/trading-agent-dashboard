Backtesting agent architecture — XAU (Gold)

Gold is the first asset through a standalone engine: it measures every driver of gold's Layer 1 call against what gold actually did next. Association only — no prediction, no formula, no trading result.

coverage-008 r2 accepted 24 Sep 2026 21 of 28 drivers measured 2023–2026 · 6,070 anchors

The engine in five moves — each move is a rule, not a step that can be skipped

1. DeclareDriver, split, horizon and context are hashed into a registry before any outcome is seen.
2. AnchorThe instants to test: weekday 14:00 UTC (964) and real releases (5,106).
3. MeasureGold's return at +1h, +4h, +24h and the 5-session close, split by endpoint kind.
4. ConditionPer driver state, then driver state × prior context, one variable at a time.
5. Publish & verifyImmutable run, content hash, then an independent re-run by the coordinator.

And three endpoint kinds, never pooled: exact 24h elapsed, delayed endpoint (the endpoint bar arrived late) and session close (the 5-session calendar end). Daily +24h is 766 exact + 198 delayed = 964; pooling them would let a missing bar look like market behaviour.

How each driver is analysed

  1. Split each driver into states fixed before outcomes: levels → above/below the driver's own median; changes → sign; events → family, field present/missing, surprise sign; age → buckets; gold returns → prior-return sign.
  2. Per state, cohort, horizon and endpoint kind: n, positive / negative / exact-zero counts, median and quartiles of the realised % return, and a year breakdown (2023–2026) summing to that state's own n.
  3. Then each state × each of 8 prior-context fields (5-session trend, 5-session realised volatility, real-yield, 2-year and 10-year changes, broad-dollar change, recent surprise state, hours since release) — one variable at a time: 1,192 daily + 7,178 event cells.
  4. min n = 20; anything below is flagged small-sample and is not a finding.

The question is narrow: does this driver's state change what gold does next — not which weight it deserves, and not whether it predicts. Weights come later, if at all.

How it is stored: plain JSON, one directory per acquisition, every file hashed in a manifest.json beside it and read-only afterwards — no research database, no warehouse write. Archives live under the canonical checkout at backtester/tmp/: gold-hourly-extended-20260918, gold-calendar-extended-20260918, gold-fred-extended-20260918; results in the gold worktree at backtester/tmp/ivr-coverage-006-20260921/. Macros and events start one to two months before the prices purely as warm-up for the 20-observation lookbacks and the daily grid; the 964 daily anchors are weekdays at 14:00 UTC inside the price window.

Two terms worth pinning down

Anchor = the t = 0 of one test: a weekday 14:00 UTC grid slot (964 of them) or a real release instant (5,106). The entry price is the close of the candle containing the anchor, available only when that candle completes an hour later — hence the disclosed entry delay. One anchor feeds every driver, horizon and cell, so the counts overlap heavily.

The 36-hour rule = FRED gives a date per vintage, not the minute the number was published, so a macro value counts as available at vintage date + 36 hours (gold_macro_vintage_dataset.js). Conservative means later than reality, never earlier, so nothing future can leak in; the cost is that a macro driver can look up to a day and a half staler than it was, and calendar- or vintage-dependent numbers stay labelled archive-fit exploratory.

Scale in one line: 964 daily + 5,106 event anchors, each scored at four horizons and four endpoint kinds in two cohorts — then repeated for every driver state and every prior-context state.
