## 1. The rule, as the deployed code states it

The trader's wrapper is `C:\ftmo2\tmp\live-trading-trader-run.cmd`, and the flags in it are the whole of lane 2's
selection: `--lane "ftmo-2" --grid half --r-multiple 3 --magic 20261005 --expect-identity
C:\live-trading\state\lane-ftmo2-identity.json --max-per-day 4`, plus `--confirm-live` once the lane is armed. Each
point the owner restated is held by a named piece of code rather than by the comment around it.

| Rule | Where it is decided | What the code does |
| --- | --- | --- |
| Same calls, same original levels | `lib/l2l_strategy.js` `buildPlan` (line 260) with `gridLevels` (149) | The direction is the sealed Layer 1 call for the asset (priority call, falling back to the 24h call), read exactly as the page reads it; the ladder is the marked `data/l2l-levels.json`. A call that is not BULLISH/BEARISH is `no-call` and trades nothing. |
| A midpoint between every adjacent pair | `halfGrid` (125) | For the ladder sorted highest first, `(a + b) / 2` is inserted between each adjacent pair, kept only when it is strictly between the two it came from, labelled `midpoint <p> between <a> and <b>`. |
| Every original level and midpoint is a trigger and a target | `gridLevels` (149) and `ticketGeometry` (232) | The grid list with midpoints is the only list the reading uses: the crossing test runs over it, and the target is `nearestAbove`/`nearestBelow` over the same list. Nothing filters by `role`, so a midpoint is both an entry line and a target line. |
| The closed-M5 crossing rule, call direction only | `buildPlan` (260) | The newest *closed* M5 bar must finish beyond a level the previous bar had not finished beyond, with one point of the instrument's own grid as the margin; the side is the call's side, so a candle crossing the other way is not a signal. |
| The entry is a limit back at the crossed level | `buildPlan`, `entry = cleared.price`, `entry_type: "limit"` | The ticket's entry is the level the candle deviated, not the close; the loop sends it as a pending limit through `tools/mt5-bridge/live-trading-order.py open`. |
| Stop one third of entry-to-target, about 3R | `ticketGeometry` (232): `risk = reward / rMultiple`, `rMultiple = 3` | The target is the next line in the trade's direction, the stop is that distance divided by three, and both are rounded to six decimals before the terminal applies the instrument's own tick: the realised R is 3 to within the symbol's grid (XAUUSD's first live reading was 4033.29 → target 3997.55, stop 4045.203333, risk 11.913 = 35.74/3). |
| A fresh setup after TP the same day, same level included | `scripts/run-live-trading-trader.js` `decisionRows` (1939) | A cycle ends on its take-profit or a turned call; after that the pair is read by the ordinary fresh-crossing path again, so a new M5 bar crossing the same level is a new signal on the same day. `tests/live_trading_lane2.test.js` states it: "after a take-profit the same day can take a fresh crossing, and the spent bar is still spent". |
| Duplicate-signal protection kept | `takenSignals` / `signalKey` (1843, 1967) | The key is `symbol|signal_time_utc`: a signal bar is spent once whether or not its ticket filled, so the same candle can never become two tickets. A re-entry at the trigger level of a standing trade is a separate path and is not a second signal. |
| Simultaneous order/position limit | the rule's own one-ticket-per-pair hold; `--max-open` absent | One working ticket per pair at a time (the owner's "each asset can have only one pending order running at a time"); there is no cap across pairs, so four pairs can work at once, and `--max-open` stays out of the command line. |
| Breakeven and trailing | `BREAKEVEN_R_MULTIPLE = 2`, `TRAIL_FROM_R_MULTIPLE = 3`, `TRAIL_BEHIND_R = 3` (231-233) | At 2R the stop moves to the placement entry, once, through the tool's `modify`. From 3R the stop follows the market, kept three times the placement risk behind the furthest price since placement (entry + 1R at 4R, and so on), never behind the stop that already stands and never at or past the target. The target is never changed. |
| What `--max-per-day` counts | `placementsToday` (1853), `todayPlacements` (1888) | Trades *placed* today in `Europe/Prague` (the zone FTMO's own day rolls on), not attempts: a ticket the tool refused does not spend the cap, and a re-entry put back at the same trigger level is the same trade and does not spend it either. Four is retained for this activation. |

The order path uses them without being told to: `run-live-trading-trader.js` passes no `--lots` and no `--max-lots`, and
`live-trading-order.py`'s `resolve_volume` (line 327) takes the symbol's `volume_min` as the base, rounds it to
`volume_step`, refuses anything below the minimum or above the run's cap, and echoes `symbol_min_volume` /
`symbol_volume_step` in its answer. Growing the size therefore takes an explicit `--lots` plus a `--max-lots` that
covers it; nothing in the lane's command line can raise it by accident. This sizing stays in force until the owner
changes it.

## 4. The registration

```powershell
cd C:\ftmo2
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\register-live-trading-trader-task.ps1 `
  -RepoRoot C:\ftmo2 -Lane ftmo-2 -Grid half -RMultiple 3 -Magic 20261005 `
  -ExpectIdentity C:\live-trading\state\lane-ftmo2-identity.json `
  -TaskName LiveTradingTraderTick-ftmo2 -ChainFeed -Published C:\live-trading\publisher `
  -Terminal 'C:\Program Files\FTMO Global Markets MT5 Terminal 2' `
  -Node 'C:\Program Files\nodejs\node.exe' -Python 'C:\Program Files\Python313\python.exe' `
  -HiddenRunner 'C:\Users\Administrator\.trading-agent-dashboard\scripts\run-hidden.vbs' `
  -MaxPerDay 4 -Arm
```

Two corrections against stage 7's draft command: `-Published` names the **publisher's checkout**
(`C:\live-trading\publisher`), which is where the calls and the ladder are read from, not `C:\ftmo2\data`; and
`-HiddenRunner` is the host's own copy under `C:\Users\Administrator\`, not this PC's `C:\Users\A17\` path. The script
kept the previous wrapper as `live-trading-trader-run.cmd.bak-20261110204620`. The registered task is
`LiveTradingTraderTick-ftmo2`, principal `Administrator` / `Interactive` / `Limited`, every 5 minutes, chain-feed with a
90 s settle, and the wrapper carries `--confirm-live` exactly once.
