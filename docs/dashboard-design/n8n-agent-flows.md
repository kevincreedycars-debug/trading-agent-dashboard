# n8n agent flows, as the Architecture map draws them

2026-11-15 · public summary · generated by `node scripts/build_factory_flows.js` from the committed
Layer 1 agent exports · presentation only

The Architecture map gives every Layer 1 core an *Inspect n8n flow* control. This page is the public-safe
record behind that diagram. It lists the nodes, the connections between them and what each step is for; it
does not reproduce node parameters, credential references, provider endpoints or workflow URLs.

A checked-in export is a saved snapshot. It establishes what the workflow looked like when it was exported.
It does not establish that the live n8n workspace runs this version today, so every flow here is labelled
either **verified** or **documented workflow**, and never "live".

## How the map reads a flow

- **Direct invocation** - the Master Orchestrator calls the agent as a workflow. That call carries no market
  data.
- **Storage hand-off** - the asset collector writes a snapshot row, and the agent reads the
  `market_snapshots` table. The row travels through storage, not through a workflow invocation.
- **The agent's own chain** - the nodes below, in the order the export connects them.
- **Storage write** - the finished call is inserted into `agent_outputs`; the Dashboard Writer publishes
  `data/layer1.json` from the newest row per asset.

### USD · USD Layer 1 Agent

- Status: **Verified flow**. The dossier walks the same export node by node and executes the scoring code against a frozen fixture. Its eight-step table omits the combine node, which the export places between the rulebook fetch and the model call; this diagram draws all nine nodes of the export.
- Export: `exports/usd_layer1_agent.json` - 9 nodes, 8 connections, sha256 `719ff071a17c…`.
- Verified by: `docs/analysis-engine/USD_LAYER1_LOGIC.md` - Verified against the export and the logic dossier.
- Joins: none. No node in this export receives more than one connection.
- Branches: none. The export connects this agent as a single chain.

| Step | Node | Type | What it is for | Inputs | Outputs |
| --- | --- | --- | --- | --- | --- |
| 03 PACK | `Build USD Input Pack` | Code | Keeps the newest snapshot that carries its date, its run time and every required input field, and names the inputs that are missing. A row that fails the test is dropped rather than partially scored. | The snapshot rows from the read step. | One input pack: the chosen snapshot, its missing-input list and the run date. |
| 06 MODEL | `Message a model` | OpenAI model | Sends the rulebook and the input pack to the model and receives a drafted reading. The draft is not the call: the scoring node re-derives every number afterwards. | The combined payload: rule text, snapshot and the output contract. | A drafted factor reading in the row contract. |
| 02 READ | `Supabase Get Many` | Supabase | Pulls every row of the market_snapshots table. No filter is applied here: sorting and the usability test happen in the next Code node, which keeps the rule readable in one place. | The market_snapshots table, through the stored Supabase connection. | Every snapshot row, sorted only by the next node. |
| 09 WRITE | `Create a row` | Supabase | Inserts the finished call into agent_outputs. This is the storage hand-off the dashboard reads; no later stage is invoked from inside this workflow. | The finished call row. | One row in agent_outputs, which the Dashboard Writer publishes. |
| 05 COMBINE | `Combine md & market snapshot` | Code | Joins the fetched rule text with the input pack into one payload for the model. It adds no rule of its own: it only assembles what the two earlier branches produced. | The logic document and the input pack. | One prompt payload carrying the rules and the snapshot. |
| 04 RULEBOOK | `Get USD Logic Document` | GitHub | Reads the agent's logic document from the repository. The rule text is fetched on every run, so the document is an input to the call rather than a copy of it. | The repository path of the agent's logic document. | The rule text, as a file the next node can combine. |
| 07 PARSE | `Parse USD Agent Output` | Code | Reads the model's answer into the row contract and flags any input the draft names as missing, so a partial reading cannot pass as a complete one. | The model's drafted reading. | A structured set of factor readings plus the missing-input flags. |
| 08 SCORE | `Calculate USD Conviction` | Code | Re-derives every factor from the raw snapshot and computes the direction and conviction deterministically. The model's own numbers are overwritten here, which is why this node is the decision and the model is not. | The raw snapshot and the parsed reading. | The call: direction, conviction, the factor signals and the missing inputs. |
| 01 TRIGGER | `When Executed by Another Workflow` | Execute Workflow trigger | The orchestrator calls this agent directly. Nothing inside the agent schedules itself, and no market data arrives through this node. | A workflow invocation from the Master Orchestrator. | One empty item that starts the chain. |

Connections, in the export's own order:

```
Build USD Input Pack -> Get USD Logic Document
Supabase Get Many -> Build USD Input Pack
Message a model -> Parse USD Agent Output
Combine md & market snapshot -> Message a model
Get USD Logic Document -> Combine md & market snapshot
Parse USD Agent Output -> Calculate USD Conviction
Calculate USD Conviction -> Create a row
When Executed by Another Workflow -> Supabase Get Many
```

## What is deliberately absent

- Node parameters, including the code nodes' source, the model settings and the table identifiers.
- Credential references and any provider endpoint. The builder rejects a URL, a key, a token, a secret, a
  webhook and a credential-shaped string before it writes either file.
- A claim of live runtime status. The export's own `active` flag describes the saved document, not the
  workspace, and the map shows it only as a property of the export.
